# Backend v3: changes and improvements

Running list of what v3 changes compared with v2 (Cloudflare Worker and Durable
Objects), and the fixes made while testing it. The plan is in
`2026-11-23-backend-v3.md`.

## Architecture

- All server state lives in one self-hosted Convex (SQLite). The test server is
  `vmate3.aster0.dev`; prod moves to `vmate.aster0.dev` at cutover.
- The phone holds one Convex WebSocket for everything server-side. Direct
  (phone → VTOP) and Udp stay outside it.
- The engine keeps no state. Sealed sessions, saved passwords, sign-ins in
  progress and rate limits are all in Convex.
- Cloudflare only takes mail in. The Email Worker hands each mail to Convex.
- `regno` lives only on `accounts`. Every other row links by `accountId`, with
  no copies.

## Identity

- Who the student is comes only from the TLSNotary proof of `/vtop/content`.
  The proof sends no cookie, so it asks for no consent. Only the session id is
  hidden, and the engine checks the page VTOP served.
- A phone proves once. `auth:token` returns a 15-minute ES256 JWT carrying
  `regno`, plus a refresh token that the device key must also sign. From then
  on the refresh token gets new JWTs, and the phone never proves again unless:
  - its tokens are revoked (reuse, a removed phone, sign-out, a deleted account)
  - it goes unused for 90 days
  - the app data is wiped
- Refresh tokens rotate on every use. Reusing an old one revokes the chain.
  A replaced token still works for the same install while its successor is
  unused, even days later, so a lost reply doesn't sign the student out. No time
  limit is needed: every refresh is signed by the device key too.
- A chain keeps three rows at most: the current token, the one just used (a lost
  answer may bring it back) and the one before (its reuse shows a stolen copy).
- A new proof revokes the phone's older refresh tokens.
- A v2 account token can be traded once for a refresh token, so students who
  already proved don't prove again.
- Removing a phone, deleting the account or signing out everywhere ends access
  at once (`device_removed`), not after 15 minutes.

## Rate limits

The hand-rolled counters were replaced with `@convex-dev/rate-limiter`. The
global proof cap counts proofs the engine starts, not tickets, so a script asking
for tickets with fresh device keys can't block everyone:

| Limit | Rule | Per |
|---|---|---|
| Proof gap | 1 per 5 s | phone |
| Proofs | 20 per hour | phone |
| Proofs the engine runs | 60 per minute, burst 20 | server, counted when the engine takes a ticket |
| Proof tickets | 600 per minute, burst 200 | server, only so fresh keys can't fill the table |
| Proofs from one address | 20 per minute | client IP, at the engine before the upgrade (campus NAT shares one) |
| Server sign-ins | 10 per 10 min, burst 5 | VTOP username |
| Server sign-ins, all | 120 per minute, burst 40 | server |
| OAuth client registration | 30 per hour, burst 10 | server |
| Session handovers | 60 per minute | account |

## Mail forwarding

- Addresses kept from v2 wait under the old owner hash (`unclaimedMailboxes`).
  The first proof by that student claims the address, so nobody redoes their
  Gmail forwarding. The old address wins over one made on v3 in the meantime,
  since Gmail forwards to it: the newer one's phones move over and it goes,
  unless the newer one got an OTP since. Of several old addresses, the one used
  last wins and the rest go.
- A phone whose address the server replaced follows it (`mail:join`), and an
  address the student deleted stays deleted: `mail:join` never makes one.
- A student has one address. Setting up forwarding again joins it; a new one
  comes only after deleting the old one.
- Mail to an address not yet claimed is accepted and dropped, so Gmail doesn't
  bounce it and switch forwarding off.
- After the update, the app rejoins an address kept from v2 once (`joined` flag).
  If the address moved, it resets "ready" and clears the old stamps.
- Old OTP mail that arrives late no longer replaces a newer code.
- Switching student, or removing a phone, deletes that phone's sealed OTPs and
  its link to every address, so no OTP reaches a phone for the wrong account.
  That includes phones the backfill put on an address of a student they were
  never linked to.
- An OTP is sealed only to phones still on the address and on that student's
  account, checked again when it is stored. A phone that left in between gets
  neither the stored copy nor the push.
- Forwarding counts as working ("On") only once an OTP has come through. Gmail's
  confirmation mail shows only that the address was added, so until then the
  sheet says "Confirm in Gmail, then create the filter" and keeps watching.
  Background sync needs forwarding to be working, not only set up.
- A phone removed on another phone forgets its address on the next OTP wait or
  leave, instead of failing with a raw error.
- When the address is gone, OTP waits stop at once with "Mail forwarding is off"
  instead of polling for 6 minutes (`CoreError::ForwardingOff`).
- OTPs come over the live `mail:inbox` query first. While it is watched, the
  wait's read is answered from the subscription with no trip to the server. FCM
  wakes an app that is closed, and polling is only the backup when the socket is
  down.
- After the update, an OTP wait that runs before the rejoin rejoins the address
  then and there, instead of forgetting it.
- The rejoin after the update starts no proof by itself. It uses the v2 token,
  or waits for the next proof the student starts.

## App

- Live queries reach the UI as Kotlin Flows (`LiveWatch`, `LiveWake`). There is
  no event log and less polling.
- Queries no longer carry a per-call flow id, so the same read is the same query:
  a read of a watched query is answered locally, and the server can cache it.
  Mutations and actions still carry it, and every call is logged with it.
- Live watches follow only while the app is on screen; in the background the
  socket can close, and FCM brings session requests.
- While a watch is open, the JWT is renewed a minute before it runs out, so the
  socket doesn't drop every watch at the 15-minute mark.
- A live watch whose identity is gone ends, and the session request watch tries
  again with back-off (up to 5 minutes) instead of every 30 s.
- The Server screen reads one live query (`screen:view`) instead of four, so a
  change anywhere (a phone joining the address, a key revoked) updates it.
- Pairing info is a socket query (`pair:info`); the app's last plain HTTP call
  to our server is gone.
- An unchanged semester writes nothing, so live account views don't re-run on
  every new JWT.
- The picked semester goes to the server whenever the phone gets a new JWT, and
  when it is changed, so MCP tools use it.
- A connected app's session request is followed live from the moment the phone
  has an identity, not only from the next app start.
- The Server and Connected apps screens follow the account live after their
  first load, even when that load was the phone's first proof.
- The OTP auto-fill row reads "Mail forwarding · not set up yet" rather than
  "Off" while its sheet has forwarding picked.
- Changing the OTP auto-fill method updates the password the server keeps, if
  it keeps one.
- Deleting the server account also forgets the forwarding address on the phone,
  and the Server screen doesn't load again by itself (that would prove and start
  a new account).
- Signing out, or signing in as another student, also disconnects Gmail, turns
  off background sync and forgets the OTP source. At a switch the last student's
  refresh token is set aside and signs the phone out of their account right
  away, so it stops getting their OTPs and session requests before the new
  student proves.
- A phone removed on the server forgets its forwarding address wherever it hears
  so (a live watch, a call, a refused refresh), so OTP waits and "Turn off" don't
  fail on it.
- A watch that failed while offline (its JWT ran out) hears the error again on
  the next socket, so it renews instead of going quiet. A watch on a removed
  phone ends and drops the identity.
- A one-off read that times out unsubscribes, and a write the phone gave up on
  isn't sent again after a reconnect.
- The session request watch starts as soon as the phone has an identity for the
  signed-in student (a refresh token, a JWT or a v2 token; a check on the phone
  every 5 s), and asks for the notification permission when a
  browser or AI app is paired. A failed answer shows a toast.
- Fetch all and background sync stop at a rejected password, cancel a half-done
  OTP sign-in when they stop, and a sync that fetched nothing doesn't clear
  "paused". Fetch all no longer counts the consent prompt or a proof against its
  page timeout.
- When forwarding turns out to be off during an OTP wait, the prompt opens.
- Network failures on the proof socket (TLS on a captive portal, a dropped link)
  read as offline.
- Server screen: clearer delete text, no remove button on this phone's own row,
  and the remove text says the phone stops getting OTPs.
- Forwarding errors read "Not set up yet" when the server doesn't know the phone.
- Whole numbers from Convex (sent as floats) decode into integer fields.
- Choosing Server fetch asks once: the "Don't ask again" in "Let the server sign
  in?" also covers the cookie dialog.
- Errors on the Server and Connected apps screens open their own Inspector flow.
- The password field hides the typed password from the accessibility tree too.
- Raw error codes and TLSNotary errors read as plain sentences, the proof shows
  its stage, and the update-required screen shows that it's working.
- The cookie consent settings row leaves out the saved password's consent.
- Developer: the server setting is named "Server" and points at Convex
  (`127.0.0.1:3210`); the dead "events waiting" line is gone.

## Server sign-in (scheduler, no polling)

- The engine's sign-in with the saved password is stepped and stateless: each
  call answers done, `otp_needed` with a sealed state, or an error.
- Convex keeps a `logins` row. When forwarded mail brings the OTP, `mail.deliver`
  schedules the next step at once; nothing polls on the server. A sign-in whose
  mail never comes ends after 5 minutes.
- A code VTOP turns down (from an older mail) is never sent twice.
- `/internal/mail-otp/await`, `otpWaiters` and the engine's waiting are gone.
- The UDP gateway signs in again with the phone's JWT (sent with the session and
  every 10 minutes, never in the first, not forward-secret message) through
  `/v1/app/login`, and the phone takes the session the gateway renewed, so the
  next fetch doesn't send the expired one back.
- A sign-in starts only for a request still waiting and not started already, and
  ends with its request, so a sign-in nobody waits for takes no later code.
- Deleting the account deletes its sign-ins in progress.
- A cached session comes back from the engine with its CSRF token.

## Engine

- Every proof's log lines carry the regno once it is verified.
- Convex's global proof cap reaches the phone as "too many proofs", and one
  address may start 20 proofs a minute. The address is the `X-Forwarded-For`
  entry `PROXY_HOPS` from the end: 1 behind hawk's Caddy, 2 once Railway's edge
  is behind it too (set it at cutover).

## Backfill and cutover

- A phone that signed out or was removed on v3 is marked (`linkedOnce`), so a
  backfill pass doesn't put it back on its old account or address.
- `/internal/export` on the v2 edge lists every Durable Object, and the Convex
  import keeps the same ids, so phones and forwarding addresses carry over.
- A test backfill from prod into vmate3 ran on 2026-11-24. At release, vmate3 is
  cleared and backfilled once more, after the v2 freeze.
- Cutover order: switch the URLs and get the build approved on Play; freeze v2;
  clear and backfill; Email Routing, then DNS; promote with update priority 5.

## Tested

- Real account on the emulator: a fresh install proves in about 5 s and joins
  the address kept from v2. All 16 pages load over the Server route, MCP works
  over vmate3, and sign-out takes the phone off the address and ends its tokens.
- Demo account sign-in.
- 108 backend tests, 302 vtop-ffi tests, 70 engine tests, and the vmate3 smoke run.

## Open

- The UDP gateway's new sign-in isn't deployed: the gateway on hawk still serves
  v2 installs. It goes out at cutover, or as a second test instance first.
- While a gateway sign-in waits for the OTP, the gateway asks Convex every 2 s
  (it has no WebSocket client).
- The forwarded OTP reaches the engine through the scheduler's arguments in plain
  text (kept by Convex for a few seconds in `logins.next`, and in the scheduler's
  history). An OTP is short-lived, but sealing it to a key from the first step
  would be tighter.
- A lost answer to a v2 token trade-in or a proof ticket means proving again.
