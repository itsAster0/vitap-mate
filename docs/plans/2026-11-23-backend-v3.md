# Backend v3: Convex owns the state

Status: plan, not started. Visual overview: https://claude.ai/artifact/LsLPijtPqwk4zv3KwDQ3Tj

## Decisions

- All server state lives in one self-hosted Convex (SQLite), on its own VPS, not
  the gateway's Linode.
- The phone talks to our servers over one domain, `vmate.aster0.dev`, almost all
  of it on one Convex WebSocket. Outside it: Direct (phone → VTOP), Udp (phone →
  gateway), FCM pushes in, and the account proof's WebSocket (see Identity).
- Cloudflare only takes mail in: the Email Worker hands each mail to Convex, and
  Convex stores it. The Worker keeps no state.
- The engine and the gateway keep no state. Anything that has to survive a
  request (sealed sessions, saved passwords, sign-ins in progress, rate limits)
  is in Convex, and Convex crons do the sweeps.
- Who the student is comes from the TLSNotary account proof (`rust/vtop-tlsn`,
  being built in parallel). After it, Convex issues a JWT and a refresh token.
  They keep working until revoked, so the student never proves again.
- The JWT carries the registration number (`regno`, not the VTOP username).
  Every function finds the student from `ctx.auth`, never from an argument.
- No backward compatibility. The app is in alpha: old apps get the forced update
  (Play update priority 5).

## Routing on `vmate.aster0.dev`

Cloudflare-proxied A record to the Convex VPS. MX records stay on Cloudflare
Email Routing. Caddy on the VPS:

| Path | To | For |
|---|---|---|
| `/api/*` | Convex 3210 | the client's WebSocket and function calls |
| `/proof` | engine (Railway), WebSocket | the TLSNotary relay; Convex HTTP actions can't upgrade |
| everything else | Convex 3211, HTTP actions | `/mcp`, OAuth (`/.well-known/*`, `/authorize`, `/register`, `/token`), `/internal/mail`, `/healthz` |

The dashboard goes on a private hostname (NetBird or Cloudflare Access).
Check before building: the Convex client only uses `/api/*`, and no HTTP action
of ours starts with `/api/`.

## Identity and tokens

The first sign-in happens on the phone, and the student types in the OTP by
hand, so nothing needs Convex before the proof. Every JWT carries a `regno`.
Before the proof, the phone can only call public functions: `guides.*` and
`udp.keys`.

1. **Sign in to VTOP:**
   - **Direct:** the phone signs in itself, then proves. `auth.proveStart` is an
     unauthenticated action that takes a vm1 signature by the device's Ed25519
     key plus the raw public key (the id is `sha256(key)[:32]`, so no lookup is
     needed). It returns a one-use ticket that lasts 2 minutes.
   - **Server or Udp route:** the engine signs in and hands the session back,
     and the phone proves with it like everyone else. The proof's socket goes to
     the engine anyway, so it doesn't need the phone to reach VTOP directly.
2. **Prove (everyone).** The phone opens `/proof?ticket=`, and the engine
   relays its TLS connection to VTOP as `vtop-tlsn` does today. On `ok`, the
   engine calls the internal mutation `auth.proofDone(ticket, regno)`.
3. **Tokens.** The phone's next signed `auth.refresh` returns its first JWT and
   refresh token. The account row is created or joined at the same moment.

Forwarding is set up after the first sign-in, so a mailbox belongs to a `regno`
from the start.

Tokens:

- **Access JWT:** ES256, 15 minutes. Claims: `sub` (device id), `regno` (once
  proved), `acct`, `aud: "vmate"`. Convex verifies it as a `customJwt` provider
  with the JWKS served inline.
- **Refresh token:** random, stored hashed with its device, rotated on every
  use, expires after 90 days unused. A refresh must also be signed by the device
  key, so a leaked token alone is useless. Reusing an old one revokes the whole
  chain.
- **Revoke:** removing a phone, deleting the account, or "sign out everywhere"
  deletes the refresh rows. Functions check that the device row still exists, so
  access ends at once instead of after 15 minutes.
- **Migration:** a phone holding a v2 account token (HS256, `account-token.ts`)
  can trade it once for a refresh token. Convex checks it with
  `ACCOUNT_TOKEN_SECRET`, so students who already proved don't prove again.
- **Demo** (`DEMO2026`): `auth.demo` issues a JWT with `regno: "DEMO2026"` and
  `demo: true`. Writes and engine calls refuse it.

## Tables

`devices` (keys, label, platform, FCM token), `refreshTokens`, `proofTickets`,
`accounts` (by `regno`: settings, semester, `sealedVault`, `sealedSession`),
`accountDevices`, `accessKeys` (hashed, scopes, outings flag), `consents`,
`sessionRequests`, `pairings`, `oauthClients`, `oauthCodes`, `mailboxes`
(address id, owner `regno`), `mailboxDevices`, `otpInbox` (sealed per device),
`events` (per device, for live queries), `signIns` (history), `logins`
(server sign-ins in progress, with sealed engine state), `udpKeys`,
`guides` (`updates`, `demo`, `forwarding`), plus rate-limiter tables.

## Engine contract (stateless)

Every call carries what it needs, and returns what Convex should keep:

- `fetch` / `fetch-batch`: sealed session in, parsed pages and updated sealed
  session out.
- `session check`: sealed session in, valid or not out.
- `login`: runs one step per call. With `sealedVault` (saved password) in, it
  answers `done(sealedSession)`, `otp_needed(sealedState)` or
  `invalid_credentials`. When mail brings the OTP, a mutation schedules the next
  step with `sealedState + otp`. The engine never waits on mail.
- `proof`: the WebSocket above. The verdict goes to `auth.proofDone`.
- `mcp`: Convex's `/mcp` HTTP action checks the access key, then forwards to the
  engine with the account's sealed session.

Only the engine holds the sealing key, so Convex stores blobs it can't open.

## Mail

The Email Worker reads the address id and OTP, then POSTs
`{ addressId, otp, receivedAt, gmailConfirm? }` to `/internal/mail` with
`MAIL_TOKEN`. That token only reaches this route, so a leaked token can't touch
accounts. If Convex doesn't answer, the Worker puts the mail on a Cloudflare
Queue and retries for up to 10 minutes. `FALLBACK_FORWARD` mail goes on as today.

Convex seals the OTP to each device on the mailbox, writes `otpInbox`, moves a
waiting `logins` row on, and pushes FCM through an action. Phones watch
`otpInbox` while a sign-in waits.

## Crons

| Every | Sweeps |
|---|---|
| 1 min | expired `proofTickets`, `pairings`, `oauthCodes`, `sessionRequests` |
| 5 min | stale `logins` (OTP never came), retries of failed FCM pushes |
| 1 h | `otpInbox` older than 15 minutes, `sealedSession` past its TTL, `events` past their window |
| 1 day | `refreshTokens` unused for 90 days, `signIns` trimmed, FCM tokens Google reports dead |

Backups aren't a Convex cron: Litestream streams the SQLite WAL to R2, and a
`convex export` to R2 runs nightly as a second copy.

## Work, in order

Each step ends with tests, and `mise run check` passes for what it touches.

1. **Spike:**
   - Run self-hosted Convex with SQLite, Litestream and Caddy on a test VPS.
   - Check that `customJwt` works self-hosted.
   - Check the Convex Rust client in vtop-ffi on Android (`.so` size).
   - Restore from Litestream once.
2. **Identity:**
   - The proof ticket and `/proof` through Caddy to the engine. TLSNotary is
     the only way to prove an account; there's no cookie check.
   - JWTs and refresh tokens with rotation.
   - Trading in a v2 account token.
   - Demo JWT.
   - Tests for reuse detection and for revoke ending access at once.
3. **State:**
   - Port accounts, links, keys, consent, session requests, pairing, OAuth and
     `/mcp` from `edge/src` into Convex, keeping the route names as function
     names.
   - Change the DO alarms (`phoneWaitSecs`, `vaultTtlSecs`) to the scheduler.
   - Start from the parked Convex branch where it fits.
4. **Engine:**
   - Make every call stateless as above, including the stepped login.
   - Drop `/internal/mail-otp/await`.
5. **Mail:**
   - Email Worker → `/internal/mail`, with the queue and retry.
   - Sealing, `otpInbox`, FCM from Convex.
6. **App:**
   - One Convex client in vtop-ffi; `Live.call` and `rememberLive` in Kotlin.
   - Server route and login over actions.
   - Remove the edge HTTP client and the Proxy route.
   - Update the extension.
   - Test on the emulator with the demo account and a real proof.
7. **Backfill:**
   - Export every DO through the Cloudflare API and import with the same ids,
     inserting only rows that don't exist yet.
   - Rehearse against a copy until the counts match.
8. **Cutover** (each prod step needs its own OK):
   1. Before anything: switch `DEFAULT_SERVER` (vtop-ffi) and the mail Worker's
      `CONVEX_URL` from vmate3 to `vmate.aster0.dev`, and get the v3 build
      approved on Play (not yet promoted), so the switch doesn't wait on review.
   2. Freeze the old Worker's writes (`FREEZE=1`). Mail still flows on purpose.
   3. Clear the test data in Convex, then run the backfill once, after the
      freeze. One pass after the freeze needs no delta (the import never
      updates a device it already has, so a delta pass would miss changed FCM
      tokens).
   4. Point Email Routing at the mail Worker, then `vmate.aster0.dev` at the VPS.
   5. Promote the new app with priority 5.
9. **Cleanup** after 30 days: delete the DO classes and the old Worker routes.
